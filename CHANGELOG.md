# Changelog

## Unreleased

- Every verb a human types has its own `/pilead:<name>` command, backed by one skill: relay 0.5.7's twenty skills (ten new: `auto`, `tier`, `plan`, `handoff`, `restart`, `resume`, `retire`, `focus`, `stop` and `route`, the last a skill file only because `/pilead:route` is the extension's own command) and a skill for each of pi-lead's own seventeen verbs (`adopt` … `whoami`). `SKILL_NAMES` in the extension and in `pilead doctor` is the one list (36 skill commands, 38 `/pilead:` commands with `status` and `route`, 37 skill files), pinned by `tests/test_command_coverage.py`; `lead-start`, `turn-end`, `escalate` and `status` have no skill on purpose.
- The documents are finished: the mode skill gains relay's mutation-budget tripwire, ops-hands pattern, externalize-state rule and do-it-yourself exception; the README gains Why, Mental model, Troubleshooting, tmux and Linux use, and every limit the batches carried (near-always-once wake delivery, the ungated unregistered and nested `pi -p`, the suppressed turn-end window, the queue, `plan bind` and `route retain` limits).
- `state.home_dir` returns an absolute path (`~` expanded, relative made absolute, symlinks not resolved), so a relative `--home` or `PI_LEAD_HOME` no longer puts a relative report path and `--home` in a packet footer.
- `pilead board` gains relay's four options — `--json`, `--out PATH`, `--lead SID` and `--live [on|off]` — and live mode: a page that reloads itself with an `updated HH:MM:SS` badge (red after three refreshes), a data file beside it, and `list`, `check`, `send`, `spawn`, `close` and `turn-end` rewrite the default page and data file (no server, no process) when config `board_live` is true or `<home>/board.json` exists; `board_live` and `board_refresh_seconds` are read keys now (see README "Board").
- tmux and Linux (claude-relay 0.5.6–0.5.8): a second backend, `vendor/relay/tmux_backend.py`, selected by `PILEAD_TERMINAL=tmux` (or `RELAY_TERMINAL`), config `terminal_app` (`"auto"` | `"iterm"` | `"tmux"`) or `$TMUX`; handles are `tmux:%N` and every handle is addressed through the backend it names (`backend.for_handle`); executors open as windows (or `--pane` splits) named and coloured in the status bar, nothing typed but the launch line; a tmux lead is live only while pi runs on its pane; banners are a status-line message, then `notify-send` on Linux; `--open` goes through `vendor/relay/platform_cmds.py` and prints the page's address when there is no opener; `pilead doctor` gains `terminal backend` (and `linux helpers` on Linux) and SKIPs its iTerm rows under tmux and on Linux; no tidy under tmux; `package.json` `os` adds `linux`.
- Executor rules gain CONTEXT HYGIENE (claude-relay a0d3161): read by line range, filter shell output, never loop on screenshots, don't re-read; the report may say `Context: hit the 120k warn` / `Context: no warn`, and gives its counts per runner.
- The last of relay's command line: `pilead report <sid> [--packet N]` prints an executor's whole report in a green frame (with a `pilead diff <sid> --open` line when its worktree has staged changes). `pilead route retain "<reason>" [--session SID]` opens a registered lead's gate grace window to the same contract as `/pilead:route retain` (`lib/pilead/route.py`; `tests/route-cases.json` is read by both test suites) and refuses an executor's or a reviewer's session. `pilead list --all` shows every executor whatever its owner. `pilead lead-start --no-rename` writes `"no_rename": true`, so the extension names no tab and nothing is painted. `pilead doctor --quick` skips the three checks that wait for pi's list of commands.
- Names: wherever a verb takes an id, a lead's project or a unique id prefix of 6+ characters works too. Each verb module declares its id arguments in `RESOLVE`, and `cli.main` passes them through one read-only resolver, `lib/pilead/names.py`. An exact id always wins, an ambiguous name is refused with the candidates (exit 2), ids from the environment are never resolved, and `pilead focus` also takes a prefix. New verb `pilead whoami [token] [--json]` (see README "Names").
- Tabs stay in order: new verb `pilead tidy [--dry-run] [--quiet] [--lead SID]` puts each lead's tab first and the executors it owns after it, in their own window (`lib/pilead/tabs.py` `groups`/`order`/`follows`/`tty_hints`/`tidy_now`), repaints each group in its lead's colour, and exits 1 when it could not be applied; `spawn` (and a rotation), a `send` that relaunched or adopted, `resume`, `restart`, `handoff`, `close-predecessor`, `adopt` and `takeover` tidy afterwards in a new process (`tabs.maybe_tidy`, one line when skipped, never changing the verb); config `tidy_tabs` is read; the ledger gains `tidy` and `tidy_skipped`, and `pilead list` names a lead whose last tidy was skipped (see README "Telling tabs apart").
- The extension has a third role: `PI_LEAD_ROLE=reviewer` (exactly; `roleFrom`) lets `read`, `grep`, `find` and `ls` through and refuses every other tool with `REVIEWER_REFUSAL`, and does no lead or executor work at all — nothing under home read, watched or written, no message, footer, banner or command — while it sets the `PI_LEAD_HELD_BY` marker; tests show a quiet lead (print or json run, or a marker held by another process) does none of the lead work added since the rule: claim recovery, wakes, the health beat, the footer, the tab name, banners, the turn-end call and the move of the lead role.
- The board shows what `pilead list` knows: `review.board_data(home, lead=None, sweep=True, write=True)` reads through `read_leads` / `read_sessions` (one parse per log, through the usage cache), and its rows carry each lead's liveness, wake, posture, colour, context, size and heaviness and each executor's tokens, cache hit rate, context, scope, effort, queue, pin, auto-close reason and an undelivered report, every unknown as `null` / `-` / `?`; warnings for undelivered reports, heavy and approaching sessions, heavy leads, stuck, stale and unknown wakes, unreadable queues and records; the version in the sub-header; `Resume`, `Focus tab` and `Retire` actions; `pilead board` run by a lead parks its finished executors as `pilead list` does; a usage cache keeps 120 characters of an error message, `limit` and the pattern it was read with (see README "Board").
- Tabs say whose they are: `pilead lead-start` writes the lead's tab `label` (`[Lead] <project>`, ` ·<sid[:4]>` when a live lead holds it) and `color` (one of six, distinct per lead) and paints its tab; executors wear their CURRENT owner's colour at every launch and are repainted on `adopt` and `takeover`; a handoff's successor takes the caller's colour; the extension names every tab with `setSessionName` and nothing is typed into a running pi any more (`spawn(..., type_name=False)`, `lifecycle.rename_tab` writes `tab_title`); new verb `pilead focus <sid|project>`; config `tab_colors` is read (see README "Telling tabs apart").
- `pilead handoff <memo.md> [--project] [--model] [--effort]` hands the lead's role to a successor lead in a new tab, registered before its first turn, on the model of the lead's last answer (or `--model`; no model, no handoff), started from a memo copy with a SUCCESSOR AFTERCARE section (`lib/pilead/handoff.py`), then moves the executors, plan and wakes; `pilead close-predecessor` closes the outgoing lead's tab by its recorded handle only; the heavy-lead 🔁 line now names `pilead handoff <note.md>`; `build_pi_cmd` gains `lead_model=`; the ledger gains `lead_handoff` and `predecessor_closed` (see README "Handoff").
- `pilead list` gains a `VER` column (the pi-lead version a lead's running pi loaded, from its health file's new `version`, else the record's `version` that `lead-start` now writes, else `?`), an `⚠ old extension:` footnote for a running lead on an older extension (`/reload` in that pi), and a CTX/TOKENS legend line after the EXECUTORS rows; the lead having looked at a report (`lib/pilead/seen.py`) no longer counts an executor's own `check`, `diff` or `verify` — `usage_snapshot`, `report_verify` and `report_reviewed` carry `caller`, and the ledger gains `report_looked_at` and `surfaced_stamp_declined`, so the auto-close sweep and escalation wait for the lead.
- A lead's role can move to another session id: `pilead takeover <old> [--as NEW_SID] [--project NAME] [--force]` (`lib/pilead/succession.py`) moves its executors, pending wake lines and plan to the new id, writes the new record (no posture carried) and the forward note `handoffs/<old>.json`, removes the old record, and is safe to repeat; `/new` and `/fork` in a lead's tab run it, `/resume` says how; a lead session whose record is gone takes and sends nothing, puts its held wakes into its successor's inbox and is named `[ex-Lead] <project>`; `pilead lead-start` removes its own forward note and a moved record keeps its project; new ledger event `lead_moved`.
- A report that finds no listener is escalated: the executor's extension runs `pilead escalate <sid> --packet <n> --json` at every settle with a report (instead of `pilead notify --no-lead`), and `lib/pilead/escalation.py` decides once per packet — `resolved` when the lead has it, the inbox line written again when it was lost, the session handed to the ONE live lead of its project when its owner is gone (`adopt` reason `fallback`; `spawn` and adoption write `owner_project` into `meta.json`), and a banner for an unreadable owner, no lead, or a lead that is not listening; `--dry-run` writes nothing; `sessions/<sid>/escalation.json`; new ledger events `escalation_resolved`, `escalation_push_failed`, `owner_fallback`. pi-lead never types into a running pi session.
- An executor's owner can change: `lib/pilead/ownership.py` works out who owns a session (`owned`, `orphan`, `unowned`, `unknown`, following forward notes in `handoffs/`); `pilead adopt <sid>… [--force]` / `--from LEAD_SID` makes the calling lead the owner (moving an unregistered old owner's inbox lines and announcing an unannounced report once); `send`, `resume <executor>` and `restart` from a lead adopt an orphan, unowned or ghost-owned session they claim and warn about one another lead owns; the executor's extension finds its owner in `meta.json` each time it reports (`resolveOwner`), so an adopted session wakes its new lead; `list`, `check` and the board name orphans and unknown owners (`orphan` in `list --json` and `check --json`); new ledger event `adopted`.
- The lead's bash write gate is wired: a registered lead's bash command with a hint of a write (`BASH_GATE_HINT`: a redirect or heredoc, a writing program, a verb-log word, a control file's name or a home marker) is put to `pilead gate --record --json` (the command on stdin, 5 s) and refused only when the gate answers `block` with a reason; a slow, failing or unreadable gate lets the command run with one warning; the lead's record `leads/*.json` is a control file of the edit gate too (`lead record`, one table `tests/control-files.json` for both languages); `awk`, `gawk`, `mawk` and `sed` are judged by their raw text (a `sed` whose script writes nothing is a read) and a `cd`/`pushd` is a plain read for the word check (`cd ~/.pi-lead && ls` passes); `/pilead:status` names the bash gate.
- A report's wake says what happened and how big the change is: the report's first line and the size of the staged diff (`pilead check <sid> --refs-only --wake`, one child, a second `wake:` JSON line), `diff:` in `pilead check` and `check --json`, a footnote and `diff` in `pilead list`; no wake for work provably committed already (`wake_skipped_landed`), a note on the wake when it is landed but unproven, and a wake whose send fails is tried three times, then left in the inbox (`wake_retry_capped`).
- The lead's turn end: when pi has settled, a registered lead's extension runs `pilead turn-end` (`lib/pilead/turnend.py`: parks finished executors, names the lead's own commits with `surface_commits`, executors approaching heavy with `ctx_warn_wake`, and a once-only "getting heavy" line with `handoff_nudge`) and sends the lines as one message, at most one per 60 seconds; `pilead turn-end --dry-run` shows it and writes nothing; `auto_wake: false` turns the lead's wake off (reports stay in the inbox, the wake reads `off`); new ledger events `handoff_nudged`, `turn_end_suppressed`, `turn_end_failed`.
- Desktop banners: `pilead notify` and `lib/pilead/notify.py` post a banner (iTerm's click-to-focus notification on the lead's tty, else `osascript`) for a report's wake, an executor with no listening lead, an executor approaching heavy and the third-packet note, each announced once (`wake/<lead>/notified/`); `pilead lead-start` records the lead's `tty`; `PILEAD_NO_NOTIFY` / `RELAY_NO_NOTIFY` switch them off; config `notify_on_wake`, `notify_via` and `executor_escalation` are read; new ledger event `banner_fallback`.
- Whether each lead's wake is working is seen at a glance: the lead's extension keeps `wake/<sid>/health.json` (a beat every 30 s, `ended` at shutdown); `pilead list` gains a last `WAKE` column (`ok`, `off`, `STALE`, `STUCK`, `?`) with a footnote per state that occurs, and `list --json` gains `wake` and `waiting`; `pilead status --statusline [--ctx-tokens N] [--ctx-window N]` prints the short line pi's footer now shows in both roles (who is busy and reported, a wake that is not ok, a heavy lead); `pilead stop` and `pilead prune` remove `wake/<sid>/` with the lead.
- A lead's wakes survive a killed process: a claimed wake stays in a claim file beside the inbox until it is handed to pi or put back, and the next drain of any lead session recovers the claim files of a process that is gone (or 60 s old) ahead of the inbox (after a kill a wake may arrive twice, never lost); failed sends of one batch are put back together, in their first claim's order; a put-back that fails is ledgered (`wake_putback_failed`), warned and retried; every delivered wake is ledgered (`wake_delivered`, `wake_recovered`); a lead instance started again after `session_shutdown` delivers again; an executor's claimed packet is kept until pi records it (`packet_recovered`, `packet_putback_failed`).
- The lead's edit gate takes claude-relay's defaults (`edit_line_threshold` 40, `grace_seconds` 120), gates only a registered lead (`leads/<sid>.json` exists: on after `pilead lead-start`, off after `pilead stop`, at the next call), gates `config.json`, `ledger.jsonl` and `leads/*.route` in home at any size (`blocked` gains `control`), and `/pilead:route` names its real grace; a verb module whose `register` fails leaves nothing in `pilead --help`; a pi that finds `PI_LEAD_HELD_BY` naming another process (started from inside a pi-lead session), or a lead in a print or json run, does no lead (or executor) work, so it never takes the lead's wake messages.
- `pilead plan [status|add|rm|done|next|bind]` and `pilead list --plan`: a lead's written plan (`plans/<sid>.json`), an ordered list of packets bound to the sessions made from them and given a state (`queued`, `in-flight`, `reported`, `done`, `closed`, `superseded`, `dead`, `unknown`) from the ledger and the sessions; `next` prints the spawn or send command and sends nothing, an unreadable plan is never written over, `stop` and `prune` keep a plan with open items, and the ledger gains `plan_add`, `plan_rm`, `plan_done` and `plan_bind` (see README "Plan").
- `pilead lint <packet>`: a zero-token, read-only sanity pass over a packet before it is sent (short/no-preconditions/ignored-declaration/front-loaded-reading/asks-to-commit/asks-to-ask warnings, haiku/opus shape hints; `--strict`, `--json`); `pilead doctor [--offline]`: twenty-one read-only checks that this machine and state dir are fit to run pi-lead (PASS/WARN/FAIL/SKIP/NOT CHECKED; `--strict`, `--json`; exit 130 on Ctrl-C). A bare `NaN`/`Infinity` anywhere in `config.json` is a doctor `FAIL` (the pi extension ignores the whole file). Doctor's git-shim refusal probe runs where git can find no repository, so a shim that fails to refuse cannot commit anywhere. See README "Packet lint" and "Doctor".
- `pilead spawn` and `pilead send` now lint the outgoing packet automatically and print any findings as advice on stderr (`PILEAD_NO_LINT=1` turns it off); doctor gains `pi session logs` and `executor logs` (both read pi's own session logs via `lib/pilead/usage.py`), its `config.json` check now gives the right reason for a `CLI_RANGES` key or an unparsable `usage_limit_pattern` instead of a blanket "outside its range", and its `state`/`executor logs`/`git shim` checks agree on one definition of "open" (neither `closed` nor `dead`) and no longer count a stray `leads/<sid>.usage.json` as a lead record.
- Each `pilead` verb is its own module in `lib/pilead/verbs/`; a new verb is a new file. No verb's flags or output changed.
- `<home>/ledger.jsonl`: an append-only event log written by the verbs and the extension (ten events, see README "Ledger").
- `<home>/config.json`: the gate threshold, new-file gating, route grace, inbox poll and default executor layout are configurable (see README "Configuration"); an out-of-range or unusable number falls back to the default for that key only.
- A verb module that fails to load is skipped with one stderr line; every other verb still works.
- Detection: `spawn`/`send` store a refs snapshot per packet; `check`, `verify`, the board and the lead's wake message report `REFS MOVED` (a commit or ref change made by any route while the executor worked); `pilead refs accept` re-baselines after the lead's own commit. A comparison that could not be made (baseline missing, unreadable or of the wrong shape, git failing, or the repository gone after a baseline was stored) is reported as `refs: not compared (<why>)` and never clears auto-commit. Requires git 2.31+.
- The lead's wake survives the lead's session ending: a wake still waiting for its refs line when the session ends is put back in the inbox, not sent, and the next lead session delivers it; a send that fails is put back too. Known limits: if the lead process is killed outright during a refs fetch, that wake is lost (the report still shows in `pilead check`, `pilead list` and the board); a put-back entry can arrive after an entry written at the same moment (order only).
- Accounting: `pilead check` prints each executor's tokens and live context read from pi's own session log (`tokens <prompt>/<output> over <n> requests · ctx <live>/<window>`, with `· heavy` / `· approaching heavy`); `pilead send` refuses a heavy session unless `--heavy-override "<reason>"` is given and prints the live context and cache hit rate; the ledger gains `usage_snapshot` and `heavy_override`; `context_warn_tokens`, `context_nudge_tokens` and `handoff_nudge_mb` are now read (see README "Accounting").
- Views: an honest status for every executor, worked out from its process, tab, report and session log (`stalled`, `paused`, `dead`, logged to the ledger); `pilead list` shows LEADS and EXECUTORS with context/token columns and footnotes (`--closed`, `--lead`, `--all-leads`, `--json` now `{leads, executors}`); `pilead check --all` / `--json`; a read-only `pilead status` line; `pilead stats` per packet and by model; live context and the usage-limit pause follow the session log's active branch; a relaunch starts with no pid file, so it reads `busy`, not `stalled`; `pilead list` caches a lead's usage in `usage/leads/<sid>.json`, and a stray `leads/<sid>.usage.json` from an older build is never read as a lead; `stats` estimates divide by all of a session's packets and its trailer reads `N of M packet(s) shown` under `--since`/`--lead`; `stall_threshold_seconds`, `lead_nudge_tokens` and `usage_limit_pattern` are now read.
- A lead id is accepted in one form only (letters, digits, `.`, `_`, `-`; first and last a letter or digit; no `..`; not ending in `.usage`; at most 128 characters), checked before anything is read or written: `lead-start` and `spawn --lead` refuse any other id with exit code 2, `status` and the extension look up no lead record for it, and an unusable `$PI_LEAD_SID` in the lead role falls back to pi's own session id with a warning.
- An executor session id is accepted in one form only (the lead id's, `.usage` ending allowed), checked before anything is read or written: `send`, `close`, `check`, `verify`, `diff` and `refs accept` refuse any other id with exit code 2 and write nothing, `spawn` refuses a topic whose id would not have that form, a session's id is the name of its directory (never the `sid` field in `meta.json`), and the extension falls back from an unusable `$PI_LEAD_SID` to pi's own id with a warning; a lead with no usable id now says so.
- Tests: every test gets the recording `osascript` stub from `tests/conftest.py` (no test file can reach the real terminal, even one with no stub of its own), and `tests/ts/rpc.test.ts` runs the real `pi` with a home of its own. Doctor skips and names a `sessions/` directory whose name is not a session id instead of reading NOT CHECKED for every session, and reads NOT CHECKED (never "no log" / "no pi session has run") when a log directory could not be read; its cut values never end inside an escape and always end with `…`. `spawn`'s refusal of a long topic gives the real limit (113); `pilead list` shows a lead under its record's file name and says when a session directory's name is not a usable session id.
- How a session ends: `pilead close --supersede BY` (shown `superseded`; `send` refuses it), `close --keep-tab` (no process signalled, no tab closed; a later `send` to its live process goes through the inbox), `pilead stop <lead_sid>` / `close --self` (the lead steps down; its files are named as they are removed and a pending wake keeps its inbox), `pilead keep <sid> [--off]` (a pin `close` and `prune` respect; a `list` footnote), and `pilead prune [--days N] [--dry-run] [--lead SID] [--all]` (deletes the state of sessions that ended long ago and of ghost lead records, never anything busy, pinned or outside home); `close` removes no file, and a plain `close` of a busy session with no report says so on stderr (see README "Lifecycle").
- Model and effort: `pilead spawn` launches every executor with an explicit model and thinking level — `--model` is optional (config `executor_default_model`, default `sonnet`), config `executor_fallback_model` replaces an alias that matches no model, a model above config `executor_model_ceiling` (default `opus`) needs `--model-override "<reason>"`, and `--effort` / a packet `EFFORT:` line / config `executor_default_effort` (default `high`) set pi's `--thinking` level; `--scope` and `--keep`; `pilead list` gains SCOPE and EFFORT, `pilead stats` EFFORT; the ledger gains `launch_options`, `model_fallback` and `model_ceiling_override`; packet lint's `EFFORT:` case of `line-ignored` becomes `effort-unparsable` (see README "Model and effort").
- The lead's bash write gate, Python half: `lib/pilead/bashgate.py` reads a lead's bash command for the shapes that provably write a file (claude-relay's parser, vendored unchanged as `vendor/relay/bash_writes.py`) and applies the routing gate's rule (`bash_write_gate` = `deny`/`log`/`off`; pi-lead's control files `config.json`, `ledger.jsonl` and `leads/*.route` are a hit at any size; the verb log under `bash_gate_logging`); read-only `pilead gate` says what it makes of a command on stdin (`--record` appends `blocked`/`would_have_blocked`); a control file is recognised however its name is cased, and for the control files every word of the command is looked at (so `touch`, `rm`, `truncate`, `install`, `ln -sf` aimed at one are writes; the plain reads `cat`, `head`, `tail`, `less`, `more`, `wc`, `grep`, `ls`, `stat`, `file`, `jq`, `diff`, `cmp` are not); a command the gate could not read says so (`parsed: no`, `"parsed": false`, `parsed: false` in its ledger event) and is a control-file write when its raw text names one together with the home; the lead's record `leads/*.json` is a fourth control file, and home and `leads/` themselves are guarded (`rm -rf`, `mv`, `find … -delete`, `cd` into them); every part the gate cannot read literally (a word with `$`, a backquote or a glob, `eval`/`bash -c`/`node -e`/`python3 -c` and the like, a here-document, anything after a `cd`) is a control-file write when its raw text names one together with a home marker (`.pi-lead`, `PI_LEAD_HOME`, the home's path); `test`, `[`, `echo`, `realpath`, `readlink`, `basename` and `dirname` join the plain reads; a control file found among the words or by the raw text is refused as one the command "names", not "writes"; `--record` writes `gate_unread` for an unread command that is allowed, and `lines` is `null`, never `0`, when unknown. Nothing calls it yet: the extension is wired in a later change. See README "Writes made through bash".
- `pilead verify --rerun` also re-runs exactly `npm test`, `npm run check` and `node --test` (argv only, never a shell, the git shim first on `PATH`, the executor's git environment), reads pytest's and node's test-runner counts per runner, and compares each with what the report declares (`node: 71 passed` / `node 71/71`); a count not read or not compared is `INCONCLUSIVE`, never a match — including a declared node count when only pytest re-ran and a declared pytest count when only node re-ran. The git shim is on every re-run, so a suite whose tests create git repositories reads `INCONCLUSIVE` or `MISMATCH` for now. See README "Re-running a report's tests".
- `pilead resume <sid>` reopens a closed or dead executor — or a crashed lead — on its own pi session, conversation intact (refused while it is alive, while its tab is still open, or when pi has no log for it, unless `--force`); `pilead restart <sid>` runs an executor's current packet again as a new conversation in a successor session `<sid>-r<N>`, closing and superseding the old one; the ledger gains `resumed`, `lead_resumed` and `restarted` (see README "Lifecycle").
- Replacing a heavy or stuck executor is cheap: `pilead retire <sid>` writes `sessions/<sid>/successor-seed.md` (an index of its packets and their reported outcomes) and closes it as superseded by `successor-seed`; `pilead spawn --seed <sid or path>` hands that seed to a new session as inherited context; `pilead send --rotate` / `--upgrade` (with `--name`, `--model`, `--model-override`) retire and spawn the seeded successor in one step, past the heaviness gate; a plain send of packet 3 or more prints a note naming `--upgrade`; `restart` records `effort_source: "config"` when the old session had no stored effort; the ledger gains `retired`, `seed_inherited` and `rotated` (see README "Lifecycle").
- Auto-close: finished executors are parked by themselves — a `reported` session whose report its lead has seen (`verify`, or the first `check` that found it) and whose claimed work has landed (claude-relay 0.5.1's rule: every claimed path resolves to one tracked file, by unique suffix when the report names it relative to a subdirectory, all of them clean, and HEAD at least as new as the report; an unresolvable or ambiguous claim is unknown and never lands; read with the real git) or has sat for `auto_close_idle_minutes` (default 60; `0` = landed only) is closed, or retired when heavy, by `pilead auto-close [--lead SID] [--dry-run]` and after a lead's own `pilead list` / `check`; never anything busy, pinned, unseen, with a pending inbox or another lead's; config `auto_close` turns it off; the ledger gains `auto_closed` and `auto_close_error`; `list --closed` footnotes `auto-closed: <sid> (<reason>)` (see README "Auto-close").
- The footer `pilead spawn` and `pilead send` append to a packet now names the report path, the `pilead diff <sid> --home <home>` command the executor runs once after its report (so the review page exists when the lead is woken) and the exact closing line; `skills/executor-rules.md` tells the executor to run it.
- A plain `pilead send` now refuses before anything is written when the session is `busy`, `stalled` or `paused` (it has not finished its current packet) or its status cannot be read at all, naming `pilead check <sid>` and `--rotate` as the ways forward; `--rotate` and `--upgrade` are unaffected, and there is no override (see README "Sending to a session that is still working").
- The git shim guards one repository — the executor's worktree's (for `verify --rerun`, the verified worktree's) and its worktrees; calls on other repositories, and `git init`/`git clone` outside it, pass to the real git, so a test suite can build its own repositories under an executor and under `--rerun`; a repository the shim cannot identify is treated as the guarded one, `GIT_COMMON_DIR` is refused and cleared at launch, and a worktree git cannot resolve gets the guard-everything shim as before (see README "git shim").
- The guarded git shim also refuses a call from another repository whose work tree lands in, or contains, the guarded repository or one of its worktrees (`--work-tree`, `$GIT_WORK_TREE`, `-c core.worktree`, the top level git names, a `worktree add` path), and a `push` / `send-pack` / `receive-pack` from another repository into it (a path, a `file://` URL, or a remote whose push URLs land there; a local-looking destination it cannot resolve, and `--receive-pack` / `--exec`, are refused); `pilead doctor` compares a session's shim with the guarded text written for its worktree, so a current guarded shim reads OK.
- The guarded git shim gives a call from another repository the guarded repository's policy when a path git would write lands there — `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, a `GIT_ALTERNATE_OBJECT_DIRECTORIES` entry, `GIT_SHALLOW_FILE` / `--shallow-file`, `GIT_GRAFT_FILE` — and for `git config --file`/`-f` naming its config (or a file it reads) and `git config --global` / `--system`; it reads `--attr-source` and `--shallow-file` as taking the next word (so `git --attr-source HEAD -C <guarded> reset --hard` is refused), and an unknown global option gets the policy (see README "git shim").
- The guarded git shim passes a call from another repository only when its subcommand is a git builtin (git 2.50's `--list-cmds=builtins`, narrowed by the installed git's own list when it prints one); an alias (plain, `!shell`, or of a builtin) or an external `git-<name>` gets the guarded repository's policy, which refuses it — so another repository's `alias.p = push <guarded> …` or `git-zap` running `git -C <guarded> …` no longer reaches it, and a test suite that uses an alias in its own temporary repository is refused there (see README "git shim").
- Every git that git itself starts goes through the guarded git shim: a call it passes through for another repository runs with `GIT_EXEC_PATH` set to a mirror of git's exec-path beside the shim (`<session>/shim/exec-path`, whose `git` and pack programs are the shim and which has no other dashed builtin), so a hook, `rebase -x`, `bisect run`, a filter, `diff.external`, `--upload-pack` or a helper running `git -C <guarded> …` from another repository is refused (77); calls that get the guarded repository's policy keep git's own exec-path, so `stash`, `fetch` and `worktree add` in the worktree still work. A stale mirror is rebuilt once, else the call gets the policy (fail closed); `pilead doctor` warns about a stale or missing mirror (see README "git shim").
- The guarded git shim lets git's own nested credential helpers (`git credential-<name>`, e.g. the keychain's `credential-osxkeychain`) and dumb-http `git http-fetch` run for another repository, scoped by their git directory (top-level `git credential-<name>` and `-c credential.helper=…` stay refused), and has a depth guard: each call counts itself in `PILEAD_SHIM_DEPTH`, and past 8 nested calls it refuses (77) with a line naming the loop before starting anything, so a `git` on `PATH` that runs the shim again stops instead of looping (see README "git shim").
- Queue: `pilead send <sid> <packet> --when-idle` queues a packet for an executor that has not finished its current packet (or already has packets queued), and `pilead queue <sid> [--cancel ID|all] [--deliver [--trigger manual|check|settle]] [--json]` shows, cancels and delivers them — oldest first, one per finished packet, through the plain send (numbered, footed and baselined at delivery); ids are never reused, an unreadable `queue.json` is never shown as empty or changed, and an interrupted delivery is neither lost nor sent twice. The plain send's waiting refusal now names `--when-idle`; the ledger gains `packet_queued`, `queue_delivered`, `queue_delivery_failed`, `queue_cancelled` and `queue_id` on `packet_sent` (see README "Queueing a packet for a busy executor").
- `pilead check` now delivers one queued packet per session it checks (trigger `check`, never for `--refs-only`; never reopening a `closed`/`dead` session), before that session's own lines; `check`, `list` and `status` all show what is queued — `check` gains `queued:`/`queue: cannot be read`/`queue: #<id> could not be delivered` text lines and `queued`/`queue_error` JSON keys, `list` gains one footnote per session (`queue unreadable`/`queue stuck`/`queue failing`/`queued`) and a `queued` JSON key, `status` gains a `queued <n>`/`queued ?` segment — with no change for a session that has no queue (see README "Queueing a packet for a busy executor").
- Queue, finished: the executor's own session asks for its next queued packet after each settle (`pilead queue <sid> --deliver --trigger settle`, run by the extension, no lead or polling involved); `send --rotate` / `--upgrade` and `restart` move the queue to the successor (a queued copy of the packet being sent is dropped; an unreadable queue or a claimed head refuses them), `close` and `retire` say on stderr that a queue is left behind, `prune` keeps a session with queued packets or an unreadable queue, auto-close never parks a session with a waiting or unreadable queue and empties a queue stuck on heaviness when it parks (`queue_cancelled_on_park`), and `verify --diff-reviewed` parks the reviewed executor (`auto_closed: reviewed`); a delivery interrupted after its packet was numbered is recovered, never sent twice; the queue lock is kept fresh while a slow delivery runs, and the lock file holds `<pid> <token>` so a process removes only its own lock. The ledger gains `queue_moved`, `queue_deduped` and `queue_cancelled_on_park`.
- Queue crash windows: an interrupted delivery is recorded as sent only when the packet it numbered holds the queued text (a plain send in between no longer swallows the queued packet), and a queue move that died midway puts each item in the successor once when it is run again (items and their `packet_queued` carry `moved_from`).
- `pilead review <sid>`: a separate headless pi (`pi -p`, on the lead's own model or `--model`, read-only tools, no extensions, by default a copy of the lead's context via `--fork`, `--fresh` without) reviews an executor's staged work from the report, the packet, the full staged diff and `verify --rerun`'s output, and answers in one fixed shape; the verb measures the index, the refs and the tracked files before and after, marks a review during which anything moved INVALID and one that did not finish or is not in the shape INCOMPLETE, saves `sessions/<sid>/review-NNNN.md`, and writes `report_reviewed` (VALID only, with new fields) or `review_failed`; `--dry-run`, `--json`, `--timeout`, `--large` (see README "Review by a second pi").
- The commit gate reads a review file from `pilead review` given to `verify --findings`: one of another packet or tree, not `VALID` (or whose `Hash:` line says the trees differ), with a `blocker` or `should-fix` finding, or not recommending commit does not clear (`NOT-CLEARED-BECAUSE-review-…`; the checks only ever add a reason not to clear, hand-written findings are unchanged); `pilead review <sid> --why` asks a separate read-only pi, never with the lead's context, about a session's state, changing nothing about that session (its `check` state is read without running `check`), and saves its answer of at most eight lines as `sessions/<sid>/why-<stamp>.md`, writing `session_diagnosed`; the `pilead-review` skill is rewritten around the verb (see README "The review file and the commit gate" and "`--why`").
- Autonomous mode: `pilead auto on|off|status` sets a lead's posture (manual waits for the human on routine in-plan steps, autonomous proceeds and announces; the stop-list stops under both), writing `auto_mode_on`/`auto_mode_off`; every `pilead lead-start` resets it to config `autonomous_mode`; `pilead list` shows an `AUTO` column and a `⚡ AUTO:` footnote; an autonomous lead's wake message carries the autonomous instruction (`details.autonomous`); `pilead verify --for-autocommit` now reads config `signoff_paths`, which adds to the built-in sign-off markers of condition 4 (see README "Autonomous mode").
